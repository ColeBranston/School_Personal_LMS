Building a **prototype** is useful on a new project/field to:

- Explore requirements with the user — **requirements capture**
- Explore concepts for a proposed system — **conceptual prototyping**
- Explore technical feasibility — **experimental prototyping**

**Evolutionary prototyping** takes this further: each phase (Requirements → Design → Build → Test → Implement) produces a new *system version*, each built with the intention of evolving into the next — rather than being thrown away.

### Prototypes as requirements bait

A prototype is a way to **collect, analyze, clarify and verify** requirements. Stakeholders struggle to describe what they want in the abstract, but react readily to something concrete — so show them a candidate solution and let their reactions surface the real requirements.

> [!quote] "Prototypes are requirements bait." — Steve McMenamin

> [!question] Questions to ask stakeholders about a prototype
> - Tell me why this would solve your problem.
> - How would this affect the rest of your business?
> - Is this addressing **all** of the problem?
> - Does this suggest some other solution?
